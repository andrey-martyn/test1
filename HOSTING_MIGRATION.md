# Подготовка и переключение каталогов хостинга

Контракт **2026-10-30.1**, первый этап:
[HOSTING_PATHS.md](HOSTING_PATHS.md), [hosting-paths.json](hosting-paths.json).
Это координация перемещения действующих TEST-модулей, не перенос TEST в production.
**Ни один шаг реального переключения на хостинге этим коммитом не выполнен.**

## Состояние подготовки

| Проект | Что известно | Что ещё должен подтвердить проект |
| --- | --- | --- |
| Аналитика | В коде есть две точные схемы размещения | Перенастройка существующих manifest/launcher, сверка ручных решений, новые cron и откат |
| Review Factory | Есть инструкция переноса и штатный backup двух SQLite | Перенастройка существующего кабинета и установленного демо-моста, сохранность материалов/модерации, cron и откат |
| Витрина | Пути магазина/storage/TEST-БД не меняются | Новая папка backup в актуальных установщиках, доступность старых rollback_id, экспортов и инструкций |
| Хостинг / общие задания | Получены инвентаризация 28.10.2026 и снимок cron панели | Актуальная карта всех задач, отсутствие пропущенных потребителей, резервные копии и общее окно переключения |

Публикация инструкций во все ветки не означает готовность этих четырёх строк.
Каждый проект отдельно передаёт отчёт ниже. Смена каталогов начинается после
подготовки всех зависимостей, чтобы два кабинета не использовали разные базы.

## Что сделать сейчас в каждом проекте

1. Обновить **свою** рабочую ветку без сброса незакоммиченных изменений.
   В начале проверить `git status --short --branch`. Витрину не переключать на
   `analytics-demo`, аналитику не переключать на ветку витрины.
2. Прочитать корневые `AGENTS.md`, `HOSTING_PATHS.md`, `hosting-paths.json`
   и этот документ. Если локальная копия старее, взять только общий контракт
   из `master`, не сливая код других приложений.
3. Найти старые пути в исходниках, install/deploy/backup/restore инструментах,
   примерах команд, manifest-ах, launchers и задачах своей установки.
   Поискать по исходникам, не выводя приватные файлы/секреты в терминал или чат:

   ```bash
   git grep -n -E 'analytics-app|analytics-private-test|analytics-private|review-factory-private-test|analytics-backups|test_frontend_backups|review-harvester-private|lavka-frontend-work'
   ```

   Совпадения в исторических документах и ZIP не исправлять механически.
   Поиск в Git не покрывает действующие конфиги и задания ADM.TOOLS: они
   проверяются отдельно локально, без публикации паролей и URL-токенов.
4. Подготовить поддержку новых путей, сохранив работающую старую схему до
   переключения. Нельзя просто поменять константу и сразу запускать её на
   установке, где данные/копии ещё в старой папке.
5. Проверить на закрытой копии: существующие данные, входы, фоновые задачи и
   механизм отката. Передать отчёт готовности. Новые функции не добавлять
   в этот этап без отдельной задачи владельца.

## Общие инструкции на FTP

Git — источник общего контракта. Для проектов вне этого Git-клона документы
можно дополнительно положить в `/home/lavkasp/lavka-speciy.com/ops/`.
Эта команда публикует **только документацию** из существующего старого клона;
она не переносит приложение, не меняет БД, cron или конфиги:

```bash
cd /home/lavkasp/lavka-speciy.com/analytics-app &&
git pull --ff-only origin analytics-demo &&
test -f HOSTING_PATHS.md && test -f HOSTING_MIGRATION.md && test -f hosting-paths.json &&
install -d -m 700 /home/lavkasp/lavka-speciy.com/ops &&
install -m 600 HOSTING_PATHS.md HOSTING_MIGRATION.md hosting-paths.json /home/lavkasp/lavka-speciy.com/ops/
```

В FileZilla это `/lavka-speciy.com/ops/`. После физического переноса источником
будет `apps/lavka-modules`, а `ops/` сохранит адрес. Обновлять эти копии вместе
с контрактом; статус в старом снимке документа не считать текущим состоянием
хостинга. Документы из других Git-веток уже находятся в их корне.

## Реальное переключение: один общий порядок

1. **Зафиксировать исходное состояние.** Проверить свежую инвентаризацию,
   действующие manifest-ы, реальные корни доменов, пути PHP, все задания
   ADM.TOOLS, процессы и версию каждого клона. Сохранить закрытую карту
   конфигов/launchers и прежних команд для отката. Не включать секреты в Git.
   Проверка аналитики до переноса:

   ```bash
   /usr/local/php82/bin/php /home/lavkasp/lavka-speciy.com/analytics-app/spice-analytics/php/bin/hosting_inventory.php --root /home/lavkasp/lavka-speciy.com
   ```

   `cron.state=unavailable` не доказывает отсутствие задач панели.
2. **Остановить всех писателей.** Завершить сохранение форм, временно закрыть
   запись в аналитику, Review Factory и TEST демо-модерацию. Приостановить их
   cron и дождаться завершения уже запущенных задач. Пауза разговоров/разработки
   не останавливает cron и пользователей. Не удалять lock-файлы вместо
   завершения процессов. HTTP-задачи рабочего магазина не относятся к этой
   остановке, если не зависят от перемещаемых каталогов.
3. **Сделать окончательные согласованные копии.** Штатный analytics backup
   включает ручные решения и конфиги; Review Factory backup — основную и
   существующую синтетическую SQLite, instance.json. Дополнительно сохранить
   остальные постоянные файлы каталогов, конфиги публичных входов и все
   прежние backup/rollback-папки. Обычная копия одного работающего `.sqlite3`
   без WAL не является согласованным снимком. Проверить читаемость и целостность.
4. **Перенести существующие каталоги по карте.** Целевые папки не должны
   содержать чужую или новую пустую установку. При конфликте остановиться,
   не сливать каталоги вслепую. Общий Git-клон переносить с `.git` и обоими
   приложениями. Закрытые данные, существующие копии и их имена сохранять.
   Не запускать обе копии приложения на запись параллельно.
5. **Перенастроить все зависимости в паузе.** Аналитика: manifest-ы и launcher;
   Review Factory: instance, launcher, установленный TEST демо-мост;
   витрина: размещение backup/restore и экспортов. Вносить точечные изменения
   проверенных полей, атомарно, с закрытой копией до изменений. `source.json`
   и MySQL не переключаются на другую среду. Установка новой БД запрещена.
6. **Обновить cron и команды обслуживания.** Сохранить прежние операции,
   расписания и лимиты, заменив пути к коду и `--data`. Не включать дубли
   старой и новой задачи. Задания с записью/публикацией не использовать как
   тест переноса. Для Review Factory проверить фактическое расписание его
   проекта: снимок панели не перечисляет все возможные способы запуска.
7. **Проверить без новых бизнес-операций.** Проверить `quick_check` всех SQLite,
   состав ручных связей/отклонений/CRM, подтверждённые страницы и фасовки,
   пользователей/роли, тексты, черновики, историю и демо-модерацию. Сверять
   состав и связи, а не только количество строк или байтовый хеш после VACUUM.
   Открыть оба кабинета и магазины, проверить ресурсы и вход, существующие
   backup/rollback_id, отсутствие старых путей в активных конфигурациях.
   Перезагрузка браузера должна читать те же постоянные данные.
8. **Возобновить и наблюдать.** После успешных проверок открыть запись,
   включить по одному прежние фоновые задания и проверить их результат.
   Зафиксировать время, версии и проверенные пути; только тогда изменить
   статус контракта с `pending` на подтверждённое новое размещение и обновить
   его копии во всех ветках/`ops`. Старые рабочие копии не удалять до сверки
   и сохранения проверенной закрытой резервной копии.

Это порядок действий, а не готовый автоматический перенос. Конкретная команда
применения каждого компонента должна быть подготовлена его проектом: сейчас
универсального проверенного `apply` для всех компонентов нет.

## Cron аналитики после завершённого переключения

В ADM.TOOLS время задаёт существующее расписание панели. Ниже сначала расписание,
затем команда; в поле команды панели не вставлять первые пять полей cron.

```text
*/15 * * * * /usr/local/php82/bin/php /home/lavkasp/lavka-speciy.com/apps/lavka-modules/spice-analytics/php/bin/competitors.php --data /home/lavkasp/lavka-speciy.com/private/analytics/test --limit 30 --seconds 55
*/5 * * * * /usr/local/php82/bin/php /home/lavkasp/lavka-speciy.com/apps/lavka-modules/spice-analytics/php/bin/cron.php --data /home/lavkasp/lavka-speciy.com/private/analytics/test
```

До переключения оставлять прежние команды. HTTP-задачи ocStore с URL
Новой почты/валют сохраняются; ключи из этих URL не переносить в документацию.

## Откат без потери выполненной работы

- Снова остановить запись, cron и процессы, сохранить последнее состояние
  уже новой установки. Возврат старого кода/пути не разрешает восстановление
  старой базы поверх новых ручных решений.
- Если после переключения были записи, переносить обратно **актуальные**
  данные с проверкой целостности, затем вернуть соответствующие прежние
  конфиги/launchers/cron. Если записей не было, это подтвердить до восстановления
  окончательного снимка. Не оставлять два независимых активных экземпляра.
- Проверить данные и старые входы, затем возобновить задания. Отметить откат
  в общем статусе, сохранив сведения о сделанных изменениях и копиях.
- Старые frontend rollback_id остаются доступными из новой backup-папки;
  откат файлов витрины не откатывает ручные решения клиентов/конкурентов.

проверки пути/БД не обходить ради отметки «готово».
