# 4. Откат

## Когда откатывать

Ошибки PHP/JS, неверная фасовка или цена в корзине, повторные покупки во время
ожидания, сломанное оформление либо существенная регрессия мобильного/десктопного
списка. Сначала закрыть дальнейшее развёртывание и сохранить диагностические
времена/сообщения без персональных данных.

## Порядок

1. Взять именно резервную копию перед этим развёртыванием. `baseline/` из пакета
   служит для сравнения и не заменяет backup текущего рабочего сайта.
2. Вернуть исходный `uni_new_data.php` либо снять только добавленные подключения,
   если после переноса были иные согласованные правки. Затем восстановить три
   изменённых JS. Заменять PHP атомарно штатным способом.
3. Два новых assets удалить только если их создал этот релиз и они больше нигде
   не используются. При существовавших ранее файлах вернуть сохранённые версии.
4. Если менялся user_css, вернуть только изменённый фрагмент/поле из своей копии.
   Сохранить более поздние посторонние настройки. При изменённом с тех пор поле
   объединить вручную вместо перезаписи старым значением.
5. Если при установке обновлялись модификации, пересобрать их установленным
   способом по возвращённым исходникам. Не копировать старый generated cache
   как основной источник модификаций.
6. Адресно обновить кэши именно этой установки, включая старые/новые версии
   assets и поле CSS при его откате. Сессию и данные магазина не очищать.
7. Проверить категорию, фасовку и цену в корзине, меню и оформление. Записать
   результат отката и фактические хеши файлов.

**Полную БД из старого дампа не восстанавливать для этой фронтенд-правки:**
это затронет заказы и другие данные, появившиеся после резервной копии.
Старый кэш всех настроек тоже не является копией одного изменённого поля.

Если после установки код уже менялся, автоматическая замена файла может
стереть эти изменения: выполнить обратное объединение по точному diff релиза.
Подготовить обратные версии до переноса, чтобы откат занимал только замену
согласованных файлов и адресную инвалидацию кэша.
