# 2. Проверка и порядок переноса

## A. Проверить комплект и текущую установку

Работать из распакованного пакета, расположенного вне публичного каталога.
Первые команды только читают файлы. Вместо /ABS/SHOP указать фактический
корень проверяемого магазина или его актуальной копии:

```bash
cd /ABS/PACKAGE
sha256sum -c SHA256SUMS
python3 tools/check_files.py /ABS/SHOP
```

Python 3.6+. Проверяющий инструмент не исполняет PHP, не читает конфиги,
не соединяется с БД, не копирует файлы и не очищает кэш. Он проверяет шесть
путей и целостность включённых исходников.

| Результат | Следующее действие |
| --- | --- |
| baseline_matches | Четыре исходника совпали, два новых файла отсутствуют; можно готовить перенос готовых файлов |
| files_already_match_release | Все шесть файлов уже этой версии; проверить настройки, кэши и приёмку |
| manual_merge_required | Есть отличия, конфликт нового файла или неполный перенос; вручную сравнить baseline, текущие файлы и files |
| invalid_package | Сначала получить целый пакет; не переносить его |

Совпадение файлов не подтверждает БД, версию темы, модификации или работу
корзины. Проверить их отдельно:

- Фактические ocStore 3.0.2.0 и активную UniShop2 1.9.0.0; версию PHP не менять.
- `items_on_mobile=2` и включённый native live-price в настройках активного магазина.
- Текущие OCMOD/vQmod и template overrides, особенно controller assets/cart/options.
- Наличие изменённого `uni_new_data.php` в DIR_MODIFICATION: сгенерированная копия
  может перекрыть источник. Найти исходную модификацию, не править её кэш вручную.
- Изолированность копии для проверки: конфиги, фактическую БД и storage,
  симлинки, платежи/рассылки/аналитику. Данные подключений в отчёт не выводить.
- Пользовательские CSS/JS темы: удалить только подтверждённые конфликтующие
  фрагменты по 05_DATABASE.md; не сбрасывать поля или все правки темы.

## B. Сверить и подготовить итоговые файлы

Если baseline_matches, готовые файлы допустимы после локальной приёмки.
При отличиях — трёхстороннее сравнение: `baseline/` → текущий исходник → `files/`.
Ориентиры функций и точный контекст приведены в 06_FILE_GUIDE.md и diff.
Не затирать отличающиеся текущие файлы полной версией из пакета.

Проверить применимость diff на актуальной копии исходников:

```bash
cd /ABS/REVIEW_COPY
git apply --check /ABS/PACKAGE/patches/mobile-category.patch
```

Команда не применяет patch. Если проверка не проходит, не использовать force
или reject как замену ревью. У LF-копии может не совпасть CRLF-контекст patch:
сверить хеши и использовать полные файлы только при подтверждённом совпадении
содержимого либо объединить вручную в сохранённом формате строк.

Проверить PHP в подготовленной версии и JS, если Node доступен:

```bash
php -l /ABS/READY/catalog/controller/extension/module/uni_new_data.php
node --check /ABS/READY/catalog/view/theme/unishop2/js/common.js
node --check /ABS/READY/catalog/view/theme/unishop2/js/live-price.js
node --check /ABS/READY/catalog/view/theme/unishop2/js/showmore-ajaxpagination.js
node --check /ABS/READY/catalog/view/theme/unishop2/js/lavka-mobile-cards.js
```

Это проверки синтаксиса; они не заменяют браузерную приёмку.

## C. Резервная копия и перенос администратором

- Сохранить текущие четыре изменяемых файла и сведения о наличии двух новых
  вне публичного каталога. Если файл с новым именем уже существует — это конфликт,
  сохранить его и объединить, не считать автоматически своим новым файлом.
- Отдельно сохранить меняемое поле CSS и сведения об источнике/магазине,
  если нужна очистка БД. Не делать откат полной БД для фронтенд-правки.
- Записать дату, исходные и итоговые SHA-256, версии модификаций и ID backup.
  После ручного слияния итоговые хеши будут своими — зафиксировать их отдельно.
- Пройти 03_ACCEPTANCE.md на актуальной копии, затем выбрать короткое окно переноса.
- Загрузить сначала два новых assets, затем три изменённых JS и последним
  `uni_new_data.php`, который подключает assets. Сохранять относительные пути
  и права; PHP заменять атомарно через временный файл и rename штатным средством.
- Если исходник перекрыт OCMOD/vQmod, пересобрать модификации установленным
  способом после переноса и проверить результат. Не обновлять все расширения.
- Выполнить точечные действия кэша ниже и повторить короткую приёмку.

В корень магазина попадают только файлы из files/. Документация, baseline,
manifest, patch, инструменты проверки и CSS-образцы БД туда не копируются.

## D. Кэши и проверка версии в браузере

- Новые CSS `lavka-mobile-cards.css?v=2` и JS `lavka-mobile-cards.js?v=1`
  добавляются через Document. В штатной UniShop2 список URL задаёт имя merged
  bundle; CSS ?v=2 создаёт новую комбинацию. Проверить реально полученный ответ.
- Существующие `common.js`, `live-price.js`, `showmore-ajaxpagination.js` тоже
  изменены. Если их URL остаются прежними и действует длительный browser/CDN
  cache, обеспечить штатное версионирование URL или адресный purge. Одна жёсткая
  перезагрузка у разработчика не обновляет кэш возвращающихся покупателей.
  Такие изменения подключения при необходимости зафиксировать отдельно.
- Удалить только относящиеся к этой установке устаревшие merged-ответы штатным
  способом. Не удалять все CSS/JS, storage, сессии или кэш соседних магазинов.
- При очистке user_css обновить его кэш настроек и generated-user-style только
  текущего магазина по 05_DATABASE.md. Сгенерированный CSS не редактировать.
- Page cache/LiteSpeed/CDN чистить только для обновляемого хоста/URL. Если
  storage обслуживает несколько магазинов, определить область очистки заранее.
- Twig не менялся: сброс редактора шаблонов и общая очистка overrides не нужны.

Сверить Network/Response и Sources: CSS weight 100, новые `.lavka-mobile-card`,
helper `cart._pending`, два новых assets и отсутствие 404/ошибок JS. Проверить
как чистый браузер, так и профиль с прежним кэшем. Решение о публикации — после
выполнения функциональных пунктов 03_ACCEPTANCE.md.
