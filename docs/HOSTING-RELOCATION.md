# Подготовка витрины к общей смене каталогов

Общий контракт **2026-10-30.1** — [HOSTING_PATHS.md](../HOSTING_PATHS.md),
[hosting-paths.json](../hosting-paths.json). Координация и отчёт готовности —
[HOSTING_MIGRATION.md](../HOSTING_MIGRATION.md).
Физический перенос хостинга ещё не подтверждён.

## Границы этой задачи

Существующий клон `/home/lavkasp/lavka-frontend-work`, TEST-магазин
`/home/lavkasp/lavka-speciy.com/test`, `test_storage` и MySQL `lavkasp_test`
остаются на своих местах. Рабочий магазин и его storage не перемещаются.
Тема, версии PHP, данные товаров и внедрённые изменения витрины не меняются
ради наведения порядка в каталогах.

Меняется только место копий/экспортов, которые зависят от общей backup-папки:

```text
Было:  /home/lavkasp/lavka-speciy.com/test_frontend_backups
Будет: /home/lavkasp/lavka-speciy.com/backups/frontend/test
```

## Задача разработчику этого проекта

1. Инвентаризировать ссылки на `test_frontend_backups` и абсолютные пути в
   `ops/`, документации, manifest-ах существующих копий и экспортов. Начать с
   константы `BACKUPS` в `ops/test_store.py`. Остальные инструменты часто
   импортируют её: проверить `ops/migrate_legacy.py`, `export_legacy.py`,
   `product_tags.py`, `product_page.py`, `product_template.py`, если файл
   присутствует в этой ветке. Не считать список исчерпывающим.
2. Подготовить поддержку нового места, не перенаправляя действующую установку
   в пустую папку до физического переноса. Не вводить несуществующие CLI-флаги
   в инструкции: сначала реализовать и проверить выбранный способ переключения.
   Значения `SHOP`, `STORAGE`, `DATABASE`, `HOSTNAME` и защита хешей сохраняются.
3. Сохранить все прежние каталоги копий, их `rollback_id`, состав, mode и
   manifest-ы. Новое расположение должно позволять найти и использовать старую
   копию. Проверить абсолютные ссылки восстановления и экспорта; при необходимости
   поддержать проверенное преобразование старого расположения на чтении manifest.
   Не делать глобальную замену в содержимом резервных конфигов или данных.
4. Сверить новую и прежнюю папки на закрытой копии. Проверить создание backup,
   доступность старых ID, отказ при изменённом исходнике/симлинке и восстановление
   в тестовой копии файлов. Не запускать `--rollback` на действующем магазине
   только ради проверки переноса. Не терять копии миграции CSS и экспортов
   активного шаблона, которые созданы отдельными инструментами.
5. Обновить актуальные команды в README/`docs`, сборщиках и **будущих** инструкциях
   handover. Старые ZIP/HTML выпуски и SHA-256 не перезаписывать. Исторические
   отчёты развёртывания остаются историческими; рядом уже добавлена ссылка
   на текущий контракт путей.
6. Передать отчёт по общей форме: commit, адаптированные файлы, проверки,
   порядок включения нового места и отката с сохранением последних копий.

## Как работать с ветками

Мобильный каталог — `codex/mobile-category`, страница товара —
`codex/mobile-product`, метки — `codex/product-tags`. В каждой ветке есть
корневой контракт. На хостинге обновлять фактически используемую ветку,
не заменять код одной задачи другой ради получения документации.
Не сливать целиком `analytics-demo` в витрину: это другой рабочий набор файлов.

## Порядок переключения

До общего окна работают старые пути. В согласованное окно завершить операции
установки/экспорта, перенести существующие копии по карте, переключить проверенные
инструменты и сверить прежние ID из новой папки. Пока обе папки существуют,
не создавать независимо новые копии в разных местах.

Это смена размещения TEST-копий, не установка новых функций и не запуск
production handover. Будущие изменения рабочего магазина по-прежнему передаются
Игорю файлами/diff для ручной проверки. Аналитика и Review Factory используют
свой процесс; их закрытые базы, зависимости и cron не исправлять из установщика
витрины. Статус общего переключения отмечается только после проверки всех проектов.

## Подготовлено в инструментах

`ops/test_store.py` теперь распознаёт две точные backup-папки: до переноса
выбирает прежнюю, после перемещения существующей папки — новую. Если существуют
обе папки или путь проходит через симлинк, операции блокируются. `SHOP`,
`STORAGE`, `DATABASE`, `HOSTNAME`, проверки файлов и алгоритм отката не изменены.
Новые CLI-флаги для установщиков не требуются. Поддержка проверена на переносе
папки со старым ID и существующими проверками установки/отката.

Перед общим переносом обновить фактически используемую ветку этого клона.
Сама команда перемещения выполняется из `analytics-demo`, как описано в
[HOSTING_MIGRATION.md](../HOSTING_MIGRATION.md#готовая-команда-переноса).
Она проверяет наличие новой поддержки в клоне витрины до изменения каталогов.
