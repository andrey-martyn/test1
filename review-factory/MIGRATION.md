> Демо-расширение `review_factory_demo` предназначено только для TEST. Его
> решения находятся в отдельной синтетической SQLite и не переходят в
> production; native-модуль проверяет и host, и фактическое имя БД. Обычный
> перенос рабочего кабинета не устанавливает это расширение в боевой магазин.

> Запросы чтения конкурентов `monitoring_requests` при переносе очищаются:
> TEST-задания с прежними product_id не исполняются после переноса.

> Текущий режим `testing` — только закрытый TEST-стенд. Его отдельная база
> `synthetic-reviews.sqlite3` не копируется `migrateCopy` и не импортируется
> в отзывы магазина. Генератор требует TEST в settings/instance.json и
> адреса test.lavka-speciy.com; на production он заблокирован. Учётные записи
> сохраняют режим testing (запись в магазин запрещена), пока не выбран
> отдельный рабочий сценарий с настоящими данными. При физическом переносе
> TEST между каталогами обе SQLite сохраняются через штатный backup.

# Перенос TEST → рабочий сайт

Это предусмотренный следующий этап. Команды ниже **не выполнялись** на хостинге.
Первый запуск и проверка UniShop2 происходят на TEST. Копирование репозитория
не означает перенос данных, расписаний или подключение к рабочей БД.

## Что сохраняется

- Тот же код модуля и отдельный вход без прав на аналитику/админку магазина.
- Личные пользователи, хеши паролей, роли, настройки, ручные поправки очереди.
- Черновики, назначения авторов, сопоставления конкурентов и их наблюдения.
- Журнал действий. Полная исходная запись каждого отправленного TEST-материала
  сохраняется в закрытом `migration_archive` вместе с прежним ID отзыва.

Активные сессии отзываются. Каталог, наличие, покупательские отзывы и агрегаты
заказов заново читаются из рабочего магазина. TEST-очередь отправки не переносится.
Уже отправленные/активированные на TEST материалы становятся **архивом TEST**.
Автор может нажать «Подготовить к рабочему сайту», перечитать материал и
отправить его заново на обычную модерацию. Это явное действие, без массовой
автоматической публикации. Несколько старых материалов не объединяются в один.

Прямое копирование test `review_id` в рабочую БД запрещено: там могут быть
другие отзывы с этими ID. Рабочий мост создаёт новые записи со статусом 0.
Исторические даты опыта сохраняются, даты публикации не переносятся задним числом.

Черновики ответов магазина и их задания также сохраняются в закрытом
`migration_archive` с префиксами `reply:` и `reply-job:`. Активные очереди
ответов и кеш отзывов TEST очищаются в новой копии: review_id другой базы
нельзя использовать для записи в рабочий магазин. После переноса нужно
выполнить `reply-sync` с production `--data` и заново выбрать реальные отзывы.
Поле source_database дополнительно запрещает исполнение задания в другой БД.

## Сверка товаров

`migrate.php plan` читает рабочий каталог только через SELECT. Автоматическое
сопоставление использует уникальные EAN, SKU и model. Одинаковый product_id
сам по себе не является доказательством соответствия. Конфликт идентификаторов,
два товара на один ID назначения и отсутствие однозначного соответствия
останавливают применение. План хранит отпечатки обоих каталогов и проверяется
повторно перед созданием копии.

Спорные товары можно явно сопоставить в закрытом JSON-файле:

```json
[{ "source_id": 123, "target_id": 456, "reason": "Проверены состав, форма, бренд и товарная карточка" }]
```

Тогда один и тот же `--map-file /PRIVATE/product-map.json` передают командам
plan и apply. Сначала проверить эти пары по карточкам; названия и похожие ID
не доказывают одинаковый состав/концентрацию. Файл должен оставаться закрытым.

## Порядок будущего переноса

1. Завершить тестирование реальной UniShop2 и фидов, сохранить отдельные закрытые
   копии комбайна и магазина. Зафиксировать, какие тестовые тексты настоящие,
   а какие относятся только к проверкам.
2. Проверить на рабочей копии `language_id` и ID статусов учитываемых заказов:
   перенос не предполагает, что эти справочники совпадают. В созданном
   production instance.json при необходимости исправить только числовые
   `language` и `statuses` перед первым `sync`.
3. Создать план. Он не меняет магазины и не останавливает авторов:

```bash
cd /home/lavkasp/lavka-speciy.com/analytics-app
/usr/local/php82/bin/php review-factory/php/bin/migrate.php plan \
  --data /home/lavkasp/lavka-speciy.com/review-factory-private-test \
  --shop-root /home/lavkasp/lavka-speciy.com/www \
  --plan /home/lavkasp/lavka-speciy.com/review-factory-migration.json
```

4. Изучить закрытый план. При `unresolved > 0` подготовить проверенные ручные
   пары и новый файл плана. Не удалять данные и не обходить сверку.
5. В согласованное окно завершить несохранённые тексты сотрудников. Создать
   **новый** production-каталог. Во время снимка SQLite-задачи и запись через
   TEST-форму приостанавливаются; исходная база не переносится и не удаляется:

```bash
/usr/local/php82/bin/php review-factory/php/bin/migrate.php apply \
  --data /home/lavkasp/lavka-speciy.com/review-factory-private-test \
  --shop-root /home/lavkasp/lavka-speciy.com/www \
  --plan /home/lavkasp/lavka-speciy.com/review-factory-migration.json \
  --destination /home/lavkasp/lavka-speciy.com/review-factory-private \
  --url https://lavka-speciy.com/review-workshop
```

Эта команда пишет только новую закрытую SQLite и конфигурацию модуля.
Она **не пишет в MySQL**, не разворачивает публичную папку, не настраивает cron
и не отправляет отзывы. Проверяются целостность SQLite и внешние ключи.
Исходная TEST-установка остаётся в режиме паузы, чтобы новые черновики не
возникали сразу в двух средах. Если перенос отменён, вернуть запись на TEST:

```bash
/usr/local/php82/bin/php review-factory/php/bin/console.php resume --data /home/lavkasp/lavka-speciy.com/review-factory-private-test
```

6. Прочитать каталог рабочего магазина в новую закрытую базу и сверить
   пользователей, черновики, назначения и журнал:

```bash
/usr/local/php82/bin/php review-factory/php/bin/console.php sync --data /home/lavkasp/lavka-speciy.com/review-factory-private
/usr/local/php82/bin/php review-factory/php/bin/console.php status --data /home/lavkasp/lavka-speciy.com/review-factory-private
```

Сопоставления конкурентов уже перенесены с заменой ID товаров. Автоматический
импорт из TEST-аналитики на рабочем сайте выключен, чтобы не вернуть старые ID.
Когда основная аналитика также будет перенесена и проверена, можно отдельно
задать её production-каталог в `analytics_data` закрытого instance.json.

7. Установить расширение в рабочем ocStore в том же порядке: таблицы через
   установку модуля, затем обновление модификаторов. Проверить рабочие ресурсы
   и записать результат проверки рейтингов в настройках расширения.
   Тестовый флаг готовности на рабочей БД сам по себе ничего не разрешает.
8. Развернуть отдельный launcher в свободную рабочую папку:

```bash
/usr/local/php82/bin/php review-factory/php/bin/console.php deploy --data /home/lavkasp/lavka-speciy.com/review-factory-private
```

9. Войти личной учётной записью, проверить права автора, сверить несколько
   товарных карточек и черновиков. Настроить новые cron с production `--data`.
   TEST-задачи остановить; не запускать обе среды для одной команды.
   Первую рабочую запись отправить вручную, сверить status=0 и дальнейшую
   активацию в штатной админке.

Изменять PHP, тариф, DNS, корневые файлы ocStore и старый source.json аналитики
для этого переноса не требуется. Закрытые базы, конфиги и копии не входят в Git.
