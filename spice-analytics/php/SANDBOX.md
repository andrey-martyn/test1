# Песочница аналитики и цен: lavkasp_test

Песочница использует существующий адрес кабинета
`https://test.lavka-speciy.com/analytics/`, но отдельный источник и отдельный
закрытый каталог. Боевые `lavkasp_lavka`, пользователь `lavkasp_analytics` и
`analytics-private` остаются без изменения. Версии PHP и тариф не меняются.

Новый пользователь — **`lavkasp_sandbox`**, доступ только к **`lavkasp_test`**.
Полный административный доступ приложению не нужен: достаточно SELECT и UPDATE.
Приложение обновляет только цену товара и поправки цены его фасовок; оно не
создаёт таблицы магазина, не удаляет записи и не меняет права MySQL.
Веб-PHP 7.3 сохраняется: кабинет ставит задания в закрытую локальную очередь,
а MySQL читает и обновляет отдельный обработчик PHP 8.2 CLI. Менять аутентификацию
БД ради старого веб-драйвера не требуется.

## 1. Создать пользователя в ADM.TOOLS

В панели «MySQL → Базы данных» раскрыть именно строку **lavkasp_test** на вашем
скриншоте и нажать **«Создать пользователя»** под этой базой.

1. Задать итоговое имя `lavkasp_sandbox`. Если панель уже подставила префикс
   `lavkasp_`, ввести только `sandbox`.
2. Создать новый длинный пароль и сохранить его в менеджере паролей. В чат его
   не отправлять и в команды не вставлять.
3. Открыть **«Привилегии»** нового пользователя. Разрешить **SELECT** и **UPDATE**
   только для `lavkasp_test`. Не выбирать «Все привилегии», INSERT, DELETE, ALTER,
   DROP, CREATE или GRANT OPTION.
4. Не привязывать этого пользователя к `lavkasp_lavka`. Старых пользователей,
   их пароли и права не менять.

Если панель поддерживает поколоночные права, для UPDATE достаточно:

- `lavkasp_test.oc_product`: поле `price`;
- `lavkasp_test.oc_product_option_value`: поля `price`, `price_prefix`.

Если доступны только привилегии всей базы, SELECT + UPDATE на `lavkasp_test.*`
поддерживаются. Код записи всё равно ограничен этими тремя полями. Проверка
отклонит пользователя с правами на другую БД, глобальными правами или GRANT OPTION.

## 2. Подготовить два представления в тестовой БД

В phpMyAdmin войти как существующий администратор **тестовой** базы (строка
`lavkasp_test` в панели), выбрать БД `lavkasp_test`, открыть вкладку SQL и выполнить:

```sql
CREATE OR REPLACE SQL SECURITY DEFINER VIEW lavkasp_test.oc_analytics_catalog_settings AS
SELECT store_id, `key`, `value`, serialized
FROM lavkasp_test.oc_setting
WHERE store_id = 0
  AND `key` IN ('config_currency', 'config_language', 'config_customer_group_id', 'config_tax');

CREATE OR REPLACE SQL SECURITY DEFINER VIEW lavkasp_test.oc_analytics_sandbox_guard AS
SELECT
  t.TABLE_NAME AS table_name,
  t.TABLE_TYPE AS table_type,
  t.ENGINE AS engine,
  (SELECT COUNT(*)
     FROM information_schema.TRIGGERS tr
    WHERE tr.TRIGGER_SCHEMA = 'lavkasp_test'
      AND tr.EVENT_OBJECT_TABLE = t.TABLE_NAME) AS trigger_count,
  (SELECT COUNT(*)
     FROM information_schema.KEY_COLUMN_USAGE k
    WHERE (k.TABLE_SCHEMA = 'lavkasp_test'
           AND k.TABLE_NAME = t.TABLE_NAME
           AND k.REFERENCED_TABLE_SCHEMA IS NOT NULL
           AND k.REFERENCED_TABLE_SCHEMA <> 'lavkasp_test')
       OR (k.REFERENCED_TABLE_SCHEMA = 'lavkasp_test'
           AND k.REFERENCED_TABLE_NAME = t.TABLE_NAME
           AND k.TABLE_SCHEMA <> 'lavkasp_test')) AS external_fk_count,
  CURRENT_USER() AS audit_user
FROM information_schema.TABLES t
WHERE t.TABLE_SCHEMA = 'lavkasp_test'
  AND t.TABLE_NAME IN ('oc_product', 'oc_product_option_value');

SELECT table_name, table_type, engine, trigger_count, external_fk_count, audit_user
FROM lavkasp_test.oc_analytics_sandbox_guard;
```

Первое представление открывает четыре настройки каталога. Второе позволяет
проверить таблицы цен с полномочиями администратора тестовой БД: пользователь
с ограниченными правами сам может не видеть установленные триггеры.
Оба представления создаёт **существующий пользователь `lavkasp_test`**, а не
новый `lavkasp_sandbox` и не администратор боевой базы. Приложение DDL не выполняет.
Новому пользователю нужен SELECT на оба представления; при SELECT на
`lavkasp_test.*` он уже предоставлен.

Последний SELECT должен вернуть ровно две строки: `oc_product` и
`oc_product_option_value`. Для обеих `table_type` — `BASE TABLE`, `engine` —
`InnoDB` или `MyISAM`, оба счётчика — 0, а `audit_user` начинается с
`lavkasp_test@`. Это блокирует запись через представления, триггеры и обнаруженные
связи с другой БД. Если результат отличается, не удалять связи и триггеры наугад:
подготовка остановится, причину нужно разобрать до переключения.

Список разрешённых полей и стандартная модель цены приведены в
[COMPETITOR_CATALOG.md](COMPETITOR_CATALOG.md). Каталог требует UAH и известного
языка/гостевой группы. Нестандартные налоги и комбинации опций не угадываются.

## 3. Остановить старые задачи аналитики и обновить код

В «Расписание задач (cron)» **поставить на паузу только задачи аналитики**:

- `.../spice-analytics/php/bin/cron.php` со старым `analytics-private`;
- `.../spice-analytics/php/bin/competitors.php` со старым `analytics-private`.

Остальные задачи основного магазина не редактировать. В WebSSH выполнить:

```bash
git -C /home/lavkasp/lavka-speciy.com/analytics-app pull --ff-only
```

Подготовка не переписывает публичный launcher. До отдельного шага переключения
кабинет продолжает работать с прежними закрытыми данными.

## 4. Подготовить отдельный закрытый каталог

В WebSSH выполнить:

```bash
/usr/local/php82/bin/php /home/lavkasp/lavka-speciy.com/analytics-app/spice-analytics/php/bin/setup_sandbox.php
```

Команда проверяет фактическую БД и имя подключённого пользователя, его права,
схему заказов и каталога. Также проверяет конфиги тестовой витрины и админки:
`DB_DATABASE=lavkasp_test`, префикс `oc_`, порт 3306 и адреса
`test.lavka-speciy.com`. Конфиги читаются как текст, их PHP не исполняется.
Пароли и содержимое конфигов не выводятся.

Для изоляции недостаточно одного имени БД. В обоих тестовых конфигах
`DIR_STORAGE` должен указывать на один отдельный каталог внутри
`/home/lavkasp/lavka-speciy.com/test/` либо на соседний
`/home/lavkasp/lavka-speciy.com/storage-test`. Сессии, кэш, логи и модификации
тестового магазина должны находиться в нём. Общий с боевым магазином storage
не допускается. Если тестовая копия его использует, сначала нужно подготовить
отдельное хранилище тестовой копии; эта команда не переписывает конфиги магазина
и не переносит его файлы. Пути `DIR_APPLICATION`, `DIR_SYSTEM` и `DIR_IMAGE`,
если объявлены, тоже должны оставаться внутри тестовой копии.

При запросе **«Пароль нового пользователя lavkasp_sandbox (ввод скрыт):»** вставить
пароль, созданный в панели, и нажать Enter. Символы не отображаются — это нормально.

Стандартный путь админки — `test/admin/config.php`. Если папка переименована,
повторить команду с её фактическим путём:

```bash
/usr/local/php82/bin/php /home/lavkasp/lavka-speciy.com/analytics-app/spice-analytics/php/bin/setup_sandbox.php --admin-config /home/lavkasp/lavka-speciy.com/test/ИМЯ_ПАПКИ_АДМИНКИ/config.php
```

`ИМЯ_ПАПКИ_АДМИНКИ` заменить фактическим именем, не вставлять строку буквально.
Если конфиг тестового магазина указывает на боевую БД или URL, подготовка
остановится с кодом причины. Самостоятельно изменять боевые конфиги для обхода
этой проверки не нужно.

Результат `state: prepared` означает, что создан
`/home/lavkasp/lavka-speciy.com/analytics-private-test`:

- новый `source.json` с доступом только к `lavkasp_test`;
- прежний пароль кабинета, но новые сессии входа;
- согласованная копия SQLite мониторинга с историей и настройками, включая WAL;
- `sandbox.json` с проверенными путями и ограничением тестовой БД;
- отдельный манифест установки.

Рабочая БД продаж, CRM, старый источник и кэш наших боевых цен сюда не копируются.
Они сохраняются в исходном `analytics-private`. Это позволяет не показывать
старый кэш боевых заказов как данные тестовой среды. После переключения CRM
песочницы будет отдельной; прежние CRM-заметки остаются в прежнем каталоге.

Новый каталог имеет права 700, закрытые файлы — 600. Повторная команда не
перезаписывает уже подготовленный каталог. При ошибке источник и публичный
кабинет остаются прежними.

## 5. Загрузить тестовые данные и проверить среду

Это команды **WebSSH**; вставить весь блок:

```bash
/usr/local/php82/bin/php /home/lavkasp/lavka-speciy.com/analytics-app/spice-analytics/php/bin/cron.php --data /home/lavkasp/lavka-speciy.com/analytics-private-test &&
/usr/local/php82/bin/php /home/lavkasp/lavka-speciy.com/analytics-app/spice-analytics/php/bin/sync_competitor_catalog.php --data /home/lavkasp/lavka-speciy.com/analytics-private-test &&
/usr/local/php82/bin/php /home/lavkasp/lavka-speciy.com/analytics-app/spice-analytics/php/bin/check_sandbox.php --data /home/lavkasp/lavka-speciy.com/analytics-private-test
```

Первая команда читает заказы только из нового источника и создаёт отдельную
локальную аналитику. Вторая читает текущие цены выбранных товаров из тестового
каталога. Последняя проверяет конфигурацию, подключение и права без изменения
магазина. При ошибке следующая команда после `&&` не выполняется.

Если тестовая БД пока не содержит заказов, обычная синхронизация может отклонить
пустую выборку. Не подменять её боевым источником: сначала подготовить нужные
тестовые данные и повторить шаг.

## 6. Переключить кабинет

После успешного предыдущего шага выполнить в WebSSH:

```bash
/usr/local/php82/bin/php /home/lavkasp/lavka-speciy.com/analytics-app/spice-analytics/php/bin/deploy.php --switch-sandbox --refresh-assets \
  --shop-root /home/lavkasp/lavka-speciy.com/test \
  --webroot /home/lavkasp/lavka-speciy.com/test/analytics \
  --data /home/lavkasp/lavka-speciy.com/analytics-private-test \
  --url https://test.lavka-speciy.com/analytics
```

Это отдельный режим переключения известной установки, а не повторное создание
кабинета. Он меняет только launcher внутри `test/analytics` и ресурсы кабинета,
проверяя подготовленную песочницу. Корневые файлы ocStore и основной `www`
не изменяются. Старый закрытый каталог сохраняется.

Обновить страницу и снова войти прежним паролем. Индикатор среды должен явно
показывать **«Песочница · lavkasp_test»**. Наши цены должны иметь источник
«База магазина», а ссылки наших товаров — вести на тестовый магазин.

## 7. Перенастроить расписание

В ADM.TOOLS изменить приостановленные задачи аналитики, заменив старый путь
данных на `analytics-private-test`, затем включить их. Не оставлять одновременно
активные старый и новый варианты одной задачи.

Аналитика продаж — поле **«Задача»**:

```text
/usr/local/php82/bin/php /home/lavkasp/lavka-speciy.com/analytics-app/spice-analytics/php/bin/cron.php --data /home/lavkasp/lavka-speciy.com/analytics-private-test
```

Мониторинг конкурентов — отдельное поле **«Задача»**:

```text
/usr/local/php82/bin/php /home/lavkasp/lavka-speciy.com/analytics-app/spice-analytics/php/bin/competitors.php --data /home/lavkasp/lavka-speciy.com/analytics-private-test --limit 5 --seconds 45
```

Для обеих задач: запуск каждые 15 минут, «Не пытаться найти нужный обработчик…
и запускать как есть» включено, не запускать новый процесс, пока предыдущий
работает. Каждая строка укладывается в лимит 240 символов. `cd`, `&&`, переменные
оболочки и перенаправление вывода в поле cron не добавлять.

Это расписание сбора данных, а не автоматическая смена цен. Каждый конкурент
и снимок нашего каталога проверяются по своей суточной готовности. Проверить
один запуск кнопкой «⚡», затем запись по расписанию во вкладке «Лог».

Для подготовки планов, записи и отката создать **третью отдельную задачу**.
Поле «Задача»:

```text
/usr/local/php82/bin/php /home/lavkasp/lavka-speciy.com/analytics-app/spice-analytics/php/bin/sandbox_prices.php --data /home/lavkasp/lavka-speciy.com/analytics-private-test --limit 3 --seconds 45
```

Здесь выбрать **«Свой вариант» → каждую минуту**: минута `*`, час `*`, день `*`,
месяц `*`, день недели `*`. Если панель показывает готовое поле выражения,
значение — `* * * * *`; в поле самой команды его не добавлять. Включить
«Не пытаться найти нужный обработчик… и запускать как есть», оставить запрет
одновременного запуска. Комментарий — «Песочница: планы и цены».

Обработчик выполняет только уже запрошенные в кабинете операции. Он не выбирает
товары и не снижает цены самостоятельно. Нажать «⚡» для первой проверки, затем
проверить новый запуск в «Логе». Без этой задачи запросы останутся в очереди.
Задание, не начатое за 10 минут, истекает. Прерванную операцию обработчик
автоматически не повторяет: часть изменений MyISAM уже могла сохраниться.
При `sandbox_job_interrupted` сначала открыть результат последнего плана и
проверить журнал; при необходимости запросить его откат. Не считать такое
сообщение доказательством, что ни одна цена не изменилась.

## 8. Первая проверка изменения цен

В модуле конкурентов выбрать один товар с подтверждённой фасовкой 50 г,
подготовить предложение и запросить серверный план. Кабинет покажет состояние
очереди и проверит результат автоматически. Обычно нужно дождаться ближайшего
минутного запуска обработчика; при занятости очередь может обрабатываться дольше.
В готовом плане проверить прежние и новые цены существующих фасовок и надпись
`lavkasp_test`.

Только отдельное нажатие **«Записать в тестовую базу»** ставит применение
просмотренного плана в очередь. Дождаться результата обработчика: само нажатие
ещё не означает успешную запись. Для отмены запросить откат того же плана и
также дождаться результата. Откат возвращает только значения,
которые по-прежнему совпадают с записью этого плана, и не затирает последующие
ручные изменения. Журнал хранится отдельно в `sandbox-prices.sqlite3`.
Очередь и её статусы хранятся в `sandbox-price-jobs.sqlite3`. После перезагрузки
кабинет восстанавливает сведения о недавних заданиях и планах. Обе SQLite входят
в резервную копию песочницы; не переносить их в публичный каталог.

Формулы и расхождения старого прайса: [PRICING_RULES.md](PRICING_RULES.md).
Отсутствующая фасовка не создаётся. Акции, нестандартные опции и неподдерживаемые
товары пропускаются с причиной. MyISAM не даёт общей транзакции нескольких
изменений: модуль использует сравнение прежних значений, журнал и компенсацию,
а при конфликте явно сообщает о неполном результате.

Закупочная стоимость пока неизвестна. План не утверждает, что предложенная цена
прибыльна; учёт себестоимости и минимальной маржи будет отдельным этапом.

## Что делать при остановке проверки

Частые безопасные коды и дальнейшее действие:

| Код | Что проверить |
|---|---|
| `test_shop_points_elsewhere`, `test_shop_url_mismatch` | Конфиги именно тестовой витрины и админки: тестовая БД и тестовый домен. |
| `test_shop_storage_not_isolated`, `test_shop_storage_mismatch` | Отдельный storage тестового магазина и одинаковый путь в обоих конфигах. |
| `test_shop_config_executable`, `test_shop_config_not_literal` | Нестандартный исполняемый конфиг не принимается как доказательство изоляции; нужен отдельный разбор, без запуска этого PHP проверкой. |
| `sandbox_schema_audit_required` | Созданы оба представления; проверочное представление создано под `lavkasp_test`, доступно SELECT и возвращает две строки. |
| `sandbox_price_tables_not_isolated`, `sandbox_schema_not_isolated` | Таблицы цен настоящие, поддерживаемого движка, без триггеров и межбазовых связей. |
| `sandbox_privileges_too_broad`, `sandbox_other_database_grant`, `sandbox_global_privileges` | У нового пользователя только SELECT + UPDATE тестовой БД; он не привязан к другой БД. |

Пришлите только JSON со статусом и безопасным `error_code`. Не присылайте
`source.json`, конфиги магазина, дамп БД, пароль или текст SHOW GRANTS.
Не меняйте старый источник, не удаляйте прежнюю SQLite и не расширяйте права
до боевой базы, чтобы обойти отказ.

Факт публикации Git-коммита не означает, что хостинг уже переключён. Переключение
считается выполненным только после команд на сервере и проверки индикатора среды.
