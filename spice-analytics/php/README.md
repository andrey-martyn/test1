После подтверждённого подключения этой установки к песочнице можно обновлять
коротким блоком из WebSSH:

```bash
cd /home/lavkasp/lavka-speciy.com/analytics-app &&
git pull --ff-only &&
/usr/local/php82/bin/php spice-analytics/php/bin/refresh_sandbox.php
```

Он проверяет существующие пути тестовой среды и вызывает только обновление
ресурсов. Настройка источника, cron и запись цен этим блоком не выполняются.

HTML и его JS/CSS теперь выдаются из одного каталога приложения через существующий
`index.php?route=/static/...`. Версия URL вычисляется из содержимого каждого файла.
Это устраняет случай, когда новое меню из Git уже видно, а публичная копия `static`
ещё содержит старый скрипт: удалённый счётчик дубликатов вызывал ошибку
`Cannot set properties of null (setting 'textContent')` во всех обычных отчётах.
Прямые старые URL ресурсов остаются совместимыми. Выдача файлов ограничена именами
JS/CSS/GeoJSON внутри static, без доступа к закрытым конфигам и без создания сессий.
Пароль, источники, данные, cron и задания изменения цен этим исправлением не меняются.

Основной вес сравнения теперь 500 г; условия доставки, оплаты и скидок собраны
во вкладке «Условия магазинов» с источниками, датами и сопоставимыми ориентирами.

## PHP магазина менять не нужно

На скриншоте ADM.TOOLS тестовый сайт использует PHP **7.3**, memory_limit **512M** и
копирует настройки с `www`. В SSH уже установлен PHP **8.2.33**. Сохраняем эту схему:

| Компонент | Исполнение |
|---|---|
| Витрина, админка и дополнения ocStore | Существующий веб-PHP 7.3 |
| Веб-кабинет аналитики | PHP 7.3+ в отдельной папке |
| Синхронизация MySQL и прогрев отчётов | Уже имеющийся PHP 8.2 CLI через cron |
| Настройка пароля, диагностические команды | Существующий PHP 8.2 CLI |

Не меняйте версию PHP сайта, encoder, open_basedir и копирование настроек ради установки.
PHP 8.2 CLI не переключает веб-версию; эта независимость описана
[хостингом](https://www.ukraine.com.ua/wiki/hosting/php/version/).
На стандартном PHP 7.3 драйвер MySQL не поддержал caching_sha2_password MySQL 8.4
(SQLSTATE/driver 2054). Поэтому синхронизация явно требует CLI 8.2; понижать способ
аутентификации БД или отключать TLS не нужно. Обычные отчёты веб-кабинета читают
закрытые снимки, подготовленные cron. Подготовка плана цен, запись и откат
в песочнице тоже выполняются через PHP 8.2 CLI: веб-кабинет ставит задания
в локальную очередь и показывает их статус. Отдельный `bin/sandbox_prices.php`
запускается раз в минуту и подключается только к проверенной `lavkasp_test`.
Открытие отчёта и веб-запросы не подключаются к MySQL; версия PHP и способ
аутентификации боевого магазина сохраняются.

Аналитика не подключает startup.php, index.php или дополнения магазина. Совместимость
конкретных установленных дополнений с PHP 8.2 не проверена: их файлов у нас нет.
Исходный дистрибутив ocStore сам по себе не доказывает совместимость всей сборки.
PHP 7.3 устарел и не поддерживается upstream; обновление магазина и дополнений следует
планировать отдельно с администратором, а не делать условием установки аналитики.

## Функции и данные

Все 13 экранов: календарь недель/лет и количество покупок 2+/5+/10+, очередь контактов,
когорты, RFM, повторные продажи, товарные сочетания, фасовки/килограммы, сезонность,
география, GA4 CSV, обратимые объединения, руководство «Практика возврата», настройки.
BCMath сохраняет точность денег.
Суммы заказов не означают подтверждённые оплаты. Сообщения покупателям автоматически
не отправляются. В production HTTPS-кабинете имена и контакты видны после входа.

Сессии и пароль кабинета отделены от магазина. Argon2id, 12 часов, ограничение попыток,
проверка host/origin, Secure/HttpOnly/SameSite=Strict cookie. Для папки cookie
`lavka_analytics_session` имеет Path=/analytics/ и не задаёт Domain.
Папка на том же origin слабее изолирована от JavaScript магазина, чем отдельный поддомен;
Path cookie не является границей защиты от XSS. Рабочая БД, конфиги, кэш и копии
должны находиться вне **всех** публичных корней. В Git их нет.

## 1. Загрузить код и проверить веб-PHP без изменения настроек

По скриншотам `/home/lavkasp/lavka-speciy.com/` содержит отдельные публичные папки
`www`, `test`, `analytics` и хранилища. Предполагаемый корень тестового сайта —
`/home/lavkasp/lavka-speciy.com/test`. Подтвердите его в «Настройки сайта».
Код и данные ниже располагаются рядом, внутри разрешённого open_basedir домена,
но **вне** этих публичных папок. Папка `analytics` рядом с `www` относится к поддомену.

Через WebSSH; репозиторий публичный. Если `analytics-app` уже существует, не заменяйте
его вслепую: сначала проверьте содержимое. Новый clone откажется писать поверх него.

```sh
umask 077
git clone --depth 1 --single-branch --branch analytics-demo https://github.com/andrey-martyn/test1.git "$HOME/lavka-speciy.com/analytics-app"
cd "$HOME/lavka-speciy.com/analytics-app/spice-analytics/php"
php bin/preflight.php
php bin/check_web.php --webroot "$HOME/lavka-speciy.com/test" --url https://test.lavka-speciy.com
```

`check_web.php` создаёт новый случайно названный временный PHP-файл, защищённый случайным
токеном и сроком 120 секунд, обращается к нему по проверенному HTTPS и удаляет файл
при успехе или ошибке. Никаких phpinfo(), паролей, конфигов магазина или заказов
не выводится. Проверяются фактический веб-PHP, расширения, Argon2id, SQLite, HTTPS,
доступ к закрытому коду внутри open_basedir и память. Конфигурация сайта не меняется.
Если сертификат/домен недоступны или не хватает расширений — сначала исправляется
эта конкретная причина; проверка TLS не отключается.

Нужны в веб-PHP: pdo_sqlite, sqlite3, bcmath, mbstring, intl, openssl и Argon2id.
Для CLI синхронизации дополнительно нужен pdo_mysql. При SQLite без SQLite3::backup нужен SQLite 3.27+
для согласованного VACUUM INTO. Памяти 512M на скриншоте достаточно с запасом;
на живом хостинге проверяется фактический расход.

## 2. Установить отдельную папку

После успешной проверки, с подтверждёнными путями:

```sh
php bin/deploy.php --shop-root "$HOME/lavka-speciy.com/test" --webroot "$HOME/lavka-speciy.com/test/analytics" --data "$HOME/lavka-speciy.com/analytics-private" --url https://test.lavka-speciy.com/analytics
php bin/configure.php --data "$HOME/lavka-speciy.com/analytics-private" --password
php bin/configure.php --data "$HOME/lavka-speciy.com/analytics-private" --source
php bin/cron.php --data "$HOME/lavka-speciy.com/analytics-private"
```

Если загрузка сообщает общую ошибку подключения, выполните в SSH:

```bash
php bin/check_source.php --data "$HOME/lavka-speciy.com/analytics-private"
```

Проверка использует тот же PHP 8.2 CLI и те же настройки TLS, что синхронизация.
Для удалённой БД сначала отдельно проверяется MySQL/TLS без передачи логина,
пароля, имени базы и SQL; проверка имени сервера и цепочки сертификатов обязательна.
Она проверяет соединение и наличие нужных столбцов в шести таблицах через
`SELECT ... LIMIT 0`, без чтения строк покупателей и без изменения данных.
Вывод содержит только этап, безопасную категорию причины, SQLSTATE и числовой
код MySQL. Значения настроек, пароль и исходный текст ошибки драйвера не выводятся.
`tls_certificate` означает проблему проверки сертификата, `authentication` —
входа пользователя, `permissions` — прав чтения, `dns` — разрешения имени сервера.
Успешная проверка соединения и схемы ещё не подтверждает завершение загрузки:
после устранения причины повторите `cron.php`.

Пароли вводятся скрыто в SSH, не через чат и не в аргументах. MySQL-пароль хранится
только в закрытом source.json с правами 600. Для входа хранится Argon2id-хеш;
повторная команда --password отзывает старые сессии. Каталоги данных 700, файлы 600.

Публичные папки имеют 755 и файлы 644 даже при SSH `umask 077`: фронтенд веб-сервера
может работать другим пользователем, чем PHP. Если использован установщик до этого
исправления и OpenCart показывает свой 404 вместо кабинета, поправьте только новые
публичные каталоги, без рекурсивного chmod и без изменения закрытых данных:

```sh
chmod 755 "$HOME/lavka-speciy.com/test/analytics" "$HOME/lavka-speciy.com/test/analytics/static"
```

Проверьте прямой вход `https://test.lavka-speciy.com/analytics/index.php?route=%2Flogin`.
Если после исправления прав там всё ещё ответ магазина, отдельно изучите правила
адресов/корень тестового сайта; не заменяйте корневой .htaccess вслепую.

Установщик отказывается писать в непустую папку, проверяет соответствие URL и пути,
размещение кода/данных вне **всего** корня сайта, включая разрешение родительских
symlink. В новую папку помещает только index.php, .htaccess, static/. Корневые
index.php/.htaccess/config.php OpenCart сохраняются. API/вход используют существующий
`/analytics/index.php?route=...`, чтобы стандартные SEO-правила OpenCart !-f/!-d не
перехватывали запросы. Настоящие правила хостинга и публичный HTTPS проверяются отдельно.

Для установки прямо в корень test сначала сохраняют существующие файлы/конфигурацию
и назначают кабинету отдельный пустой корень через панель; текущую копию не удаляют.
Для отдельного поддомена нужны DNS и сертификат; --shop-root не требуется при URL без пути.
Веб-PHP и дополнения основного магазина остаются без изменений во всех этих вариантах.

## 3. MySQL и расписание

### Обновление установленного кабинета

После `git pull --ff-only` обновите публичные ресурсы существующей установки:

```bash
php bin/deploy.php --refresh-assets --shop-root "$HOME/lavka-speciy.com/test" --webroot "$HOME/lavka-speciy.com/test/analytics" --data "$HOME/lavka-speciy.com/analytics-private" --url https://test.lavka-speciy.com/analytics
```

Режим сверяет закрытый `deployment-php.json` и существующий launcher с указанными
путями. Копирует только `analytics/static`, запрещает символические ссылки назначения.
Файлы магазина, launcher, `.htaccess`, пароль, параметры MySQL, база и CRM остаются
прежними. Обычная установка без этого флага по-прежнему отказывается писать в непустую
папку. После обновления выполните существующий `cron.php` и обновите страницу браузера.

Для обновления только интерфейса, включая руководство и мобильную таблицу дубликатов,
повторный запуск cron не требуется: достаточно pull, `--refresh-assets` и обновления
страницы. На экранах шириной до 720 px чекбокс и оба контакта занимают ширину таблицы
до начала дополнительных столбцов. Длинные имена и email переносятся; совпавшие поля
и число заказов доступны справа на скролле. Зона нажатия чекбокса — 44×44 px.
Кнопка объединения продублирована под пагинацией, с тем же выбором и предупреждением
о цепочках общих контактов. Оба экземпляра блокируются на время операции.

### История, справка и пары контактов

В периодах доступен «За всё время» (`year=0` в API/CLI). Годы теперь календарные,
с 1 января по 31 декабря. Недельные ячейки привязаны к дате понедельника и обрезаются
границами года и датой проверки: декабрь не перемещается в следующий отчёт из-за ISO.
В общей сводке уникальные покупатели считаются один раз; годовые количества не
суммируются как число людей. В календаре всей истории ячейки — годы; в товарах и
городах доступны раскрывающиеся годовые итоги. Настройки статусов, валюта и дата
проверки применяются и к полной истории. RFM, напоминания и когорты по-прежнему
опираются на всю историю до даты проверки, что поясняется справкой.

Сезонность месяцев — вертикальные столбики по заказам или сумме, с отдельными сериями
годов в режиме всей истории. Значки `?` открывают пояснение при наведении, фокусе
или нажатии; Escape закрывает справку. В справке описаны формулы, ограничения и
следующие действия для удержания клиентов.

Совпадения представлены парами с полным списком совпавших полей, фильтром и сортировкой.
Пакетный `/api/identity/merge-pairs` принимает до 100 пар, проверяет всю выборку в
одной транзакции и сохраняет только рёбра выбранных строк. Независимые пары не
склеиваются между собой. Пересекающиеся пары образуют цепочку, показанную до нажатия.
Если совпадения устарели, весь пакет отклоняется с 409. Отмена ручных связей остаётся
в карточке покупателя. Исходный магазин при объединении не изменяется.

Отдельный пользователь SELECT-only на oc_order, oc_order_product, oc_order_option,
oc_order_total, oc_order_history, oc_order_status. Не нужны INSERT/UPDATE/DELETE/DDL,
oc_customer, административные сессии, пароли клиентов, платёжные реквизиты и строки улиц.
Берутся имя, контакты, населённый пункт/регион/страна, IP, суммы, товары и выбранные опции.
Префикс таблиц настраивается. Синхронизация заказов исходную БД не изменяет.
Отдельное исключение — явно подтверждённый план цен в проверенной песочнице:
он может обновить три разрешённых поля цен только в `lavkasp_test`.

Удалённая MySQL — только проверяемый TLS с CA и именем сервера. Также поддержаны
локальный сокет/loopback защищённого SSH-туннеля. Не отключайте проверку сертификата.
InnoDB читается в consistent read-only snapshot. MyISAM — два совпавших полных чтения
с паузой и повторами; это проверка стабильности, не транзакционная гарантия.
Правки старых заказов, удаления и изменения дочерних строк также обнаруживаются.
Замена локальных записей транзакционная, сохраняет CRM/настройки/ручные связи/GA4.
Ошибки оставляют прошлые данные; последний успех/ошибка видны в кабинете.

Начальный cron — каждые 15 минут, с настоящими абсолютными путями к **PHP 8.2 CLI**
(уточнить command -v php) и файлам. Пример структуры команды:

```text
*/15 * * * * /ABS/PHP82 /ABS/lavka-speciy.com/analytics-app/spice-analytics/php/bin/cron.php --data /ABS/lavka-speciy.com/analytics-private >> /ABS/lavka-speciy.com/analytics-private/cron.log 2>&1
```

Cron исключает перекрытие задач и прогревает текущие отчёты для двух последних лет.
Кэш ограничен 32 отчётами, изменения CRM/данных отзывают его. Вкладка проверяет
обновления раз в минуту и сохраняет открытую редактируемую карточку. Сначала измерьте
нагрузку CPU/RAM/БД на тарифе; при достаточном запасе можно уменьшить интервал до 5 минут.
Сам выбор папки или поддомена не меняет общие лимиты хостинг-аккаунта.

## География, GA4 и резервные копии

Русские/украинские названия и области объединяются по локальному справочнику,
пустой город при явном самовывозе в Одесе восстанавливается по месту получения.
Исходные заказы сохраняются. Доли и сравнение лет находятся на странице «Где покупают»;
техническая проверка источников и оставшихся пропусков свёрнута в настройках. Правила и диагностика: [GEOGRAPHY.md](GEOGRAPHY.md).

IP не отправляются внешним API. Нужен отдельный легальный City MMDB; официальный
MaxMind reader 1.14.0 включён с лицензией и provenance. Тестовая MMDB служит только
для тестов и не подходит для географии покупателей. Состояние установленной геобазы
видно в отчёте; без неё IP остаются неопределёнными.
GA4 — импорт CSV и сопоставление transaction_id=order_id; аккаунт и живые отчёты не подключены.

```sh
/usr/local/php82/bin/php bin/import_geoip.php --data /home/lavkasp/lavka-speciy.com/analytics-private-test --file /PRIVATE/geoip-city.mmdb.gz
/usr/local/php82/bin/php bin/backup.php --data /home/lavkasp/lavka-speciy.com/analytics-private-test --destination /home/lavkasp/lavka-speciy.com/analytics-backups-test
```

Копия — SQLite Backup API на новом PHP, согласованный VACUUM INTO на PHP 7.3,
с проверкой quick_check; включает CRM/закрытые конфиги, исключает активные сессии.
Если мониторинг инициализирован, также включается `competitors.sqlite3` с целями,
наблюдениями и историей изменений. Для каждой БД создаётся согласованный снимок;
моменты двух снимков могут различаться. Старая установка без БД конкурентов
копируется как прежде. Ошибка любой включённой БД не публикует готовую копию.
Проверка публичных путей выполняется до mkdir/chmod. Ежедневный cron и хранение
копий настраиваются отдельно; автоматического удаления старых копий нет.

## Проверено в песочнице

На настоящих PHP 7.3.33 и 8.2: бизнес-правила, Argon2id/вход/выход/лимиты, все
12 экранов, CRM/GA4, карты/мобильный вид. Все поля прежнего контракта отчётов
2026, 2025, начала 2021 совпали с эталоном на 4917 заказах/34510 товарных строках. В PHP 7.3 добавлены
стабильные сортировки и fallback имени Europe/Kiev для старой tzdb; отчёт использует
киевское время. На полной выгрузке также проверены итоги всей истории и годовые разрезы.
Расход памяти и время первого расчёта проверяются отдельно от работы кэша;
результаты песочницы не являются обещанием скорости на хостинге.

Проверена связка PHP 8.2 CLI → HTTPS → PHP 7.3 веб-проверка с настоящей проверкой
сертификата и удалением временного файла при успехе/ошибке TLS. MySQL 8.4 проверяется
на синтетической БД через CLI 8.2: SELECT-only, MyISAM/InnoDB, изменения/удаления,
сохранение CRM, проверяемый TLS. PHP 7.3 CLI для этой синхронизации не поддерживается;
проверка с современным способом аутентификации выявила код ошибки 2054.

Docker и Python нужны только для разработки/проверок. Runtime включает только PHP,
frontend и локальный GeoIP reader. Образы разработки закреплены digest; PHP 7.3
использует подписанные пакеты ICU 67.1-7 из основной Bullseye-ветки, поскольку security
индекс в прокси ссылался на недоступные .deb. TLS/подписи пакетов не отключались.
Никакого Docker, Python, Composer или платного Python-хостинга на сервере не нужно.

## CRM реактивации и работа с ChatGPT

В очереди есть списки «К контакту сейчас», «В работе», «Вернувшиеся», «Остановлены» и
«Все кандидаты и история». CRM использует всю историю до даты проверки, независимо
от выбранного года. Предупреждения проверяют email, телефон и полное имя каждого
профиля; совпадения требуют ручной проверки. Большие группы также отмечаются,
с ограниченным списком профилей для просмотра.

Ценность — относительная сумма заказов выбранной валюты: золото при минимум двух
заказах и сумме не ниже 80-го перцентиля, серебро при повторных покупках и сумме не
ниже медианы, остальные — бронза. При равных суммах доли классов не обязаны быть
20/30/50%. Это не маржинальность или LTV-прогноз. Золотым по умолчанию назначена Таня;
поле ответственного вводится сотрудником, отдельные учётные записи ещё не реализованы.

Рабочий процесс:

1. Проверить совпадения контактов, прошлые покупки и запреты обращения.
2. Открыть «Сценарий и журнал»: знакомые товары, фасовки, совместные покупки и сценарий
   по давности паузы. Причины ухода выясняются у покупателя, а не выводятся из товаров.
3. После фактического обращения записать «Начать попытку», время в Киеве и окно
   30/60/90/180 дней. Дальнейшие разговоры добавляются к этому окну. Чеклист сохраняет
   канал, результат, причины, предложение/купон, следующую дату и ответственного.
4. Скопировать подготовленный запрос в свой чат ChatGPT, затем сохранить ответ обратно
   отдельной записью. По умолчанию запрос не включает имя, email, телефон и свободный
   текст заметок. Текст заметок можно добавить явно после проверки. Свой чат может
   иметь ограничения тарифа; API и дополнительная оплата API не нужны.
5. После очередной синхронизации проверить новый заказ, его статус и сумму. В карточке
   остаются все попытки, а в очереди — отметка результата и фильтр вернувшихся.

Встроенный сценарий — правила, а ответ ChatGPT — вручную сохранённый текст. Модель
не запускается на хостинге и не отправляет сообщения, купоны или команды приложению.
Сохранённый ответ не снимает запрет контакта. Повторный контакт после отказа допускается
после явного изменения договорённости в основной карточке. Два обращения без ответа
за 30 дней дают рекомендацию паузы. Более долгая пауза в покупках меняет этап и повод
разговора; она не означает увеличение частоты сообщений.

Используются приёмы winback: выяснение причины, устранение барьера, релевантное
предложение, согласованный следующий шаг и измерение результата. Руководство ниже
дополняет их пересказами из предоставленных книг, отделяя авторские идеи от наших
сценариев для магазина.

### Как считается возврат

До начала попытки должна быть хотя бы одна учитываемая покупка. Первый новый заказ
нужен строго после времени обращения и внутри окна. Дата проверки, валюта и выбранные
статусы применяются как в остальных расчётах. Ручное завершение сокращает окно;
попытки на одном профиле не могут пересекаться. Если объединение профилей принесло
пересекающиеся попытки, начало следующей завершает предыдущую: заказ учитывается
один раз. Такие укороченные пересечением окна исключены из доли завершённых окон.

Показываются уникальные вернувшиеся покупатели, сумма первых заказов по попыткам и
доля возврата среди завершённых окон. Ранние возвраты видны сразу, а в долю завершённых
попадут после конца окна. Незавершённые окна показаны отдельно. Суммы — суммы заказов,
а не оплаты/прибыль. Наблюдаемый возврат после контакта не доказывает его причинный
эффект: для этого нужна отдельно спланированная контрольная группа. Купон в журнале
не доказывает применение купона в заказе. Контакты задним числом помечаются отдельно.

При изменении статуса заказа результат пересчитывается; отмена может убрать ранее
показанный возврат. Журнал не затирается синхронизацией. События привязаны к исходному
профилю и сохранённым номерам заказов, поэтому объединение показывает общую историю,
а отмена объединения возвращает записи исходным профилям. Отмена ошибочной записи
хранит её с причиной и исключает из расчёта, не снимая запрет контакта автоматически.

Новая таблица `crm_events` добавляется в закрытую SQLite через `CREATE TABLE IF NOT EXISTS`.
Старые CRM-отметки и исходная БД магазина сохраняются. Перед обновлением установки
сделайте закрытую копию существующей командой `bin/backup.php`; пароль и источник БД
перенастраивать не нужно. Полная резервная копия включает журнал CRM.

HTTP-маршруты защищены тем же входом и проверкой origin:
`GET /api/crm/customers/{id}`, `POST /api/crm/customers/{id}/events`,
`POST /api/crm/events/{id}/void`. Повтор одного UUID с тем же содержимым не создаёт
дубликат события; другое содержимое с тем же UUID получает 409. Отмена сохраняет
историю. Старый `/api/customers/{id}/action` остаётся совместимым.

## Практика возврата и удержания

В боковом меню добавлен отдельный раздел для Тани: быстрый старт, восемь сценариев
по сегментам, удержание лояльных, разговор и возражения, оценка результата и источники.
В каждом сценарии есть проверка карточки, цель, порядок действий, черновик сообщения,
предложения, следующий шаг и переход к соответствующим покупателям. Численность
берётся из текущего отчёта: вся история выбранной валюты до даты проверки, с учётом
выбранных статусов. Счётчик сегмента не равен числу разрешённых контактов в очереди.

Удержание включает восемь тем, рабочий ритм и идеи пользы без обязательных скидок.
Есть поиск по руководству, ссылки на главы и печать всего руководства / сохранение
через диалог печати браузера в PDF. Это справочный интерфейс: он не создаёт событий
CRM, не запускает рассылки и не передаёт тексты во внешний ИИ.

Использованы предоставленные тексты Дэвида Аврина, Мюррея и Нейла Рафел
(`client.txt` — «Как завоевать клиента») и восстановленные релевантные фрагменты
Бориса Саркисяна («Эффективный тренинг продаж», 2007). Краткие пересказы снабжены
ссылками на главы/разделы; сообщения и сценарии адаптированы для магазина.
Оригиналы Griffin/Lowenstein, Манна/Турусиной и Spinos не предоставлены, что явно
указано в библиографии. Полные книги, извлечённые тексты и вложения не входят в Git
или архивы. Исторические проценты из литературы не представлены как результаты магазина.

Обновление этого раздела требует только `git pull --ff-only` и существующей команды
`bin/deploy.php --refresh-assets` с путями установки из раздела обновления.
Настройки PHP, пароль, источник MySQL, SQLite и журнал CRM не меняются; запускать
синхронизацию заново ради руководства не нужно.

Проверка `ANALYTICS_PHP_IMAGE=lavka-php73-dev .venv/bin/python php/tests/manual_browser_check.py`
использует синтетических покупателей: все восемь сегментов, изменение даты проверки,
переход к правильным покупателям/CRM, источники, поиск, клавиатуру, печать и мобильный
вид. В справочном разделе проверяется отсутствие изменяющих запросов и внешних запросов.


## Главный экран «Сегодня» (пилот)

Нажатие столбца открывает заказы, действие — CRM или источник изменения цены.

Остатки, обращения и себестоимость пока обозначены как неподключённые источники.

Диагностика из настроек, примеры неопределённых имён и вкладки конкурентов: [DIAGNOSTICS.md](DIAGNOSTICS.md).
