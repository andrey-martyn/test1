# Закрытый кабинет на существующем хостинге

**Решение пользователя: остаёмся на «Быстром», используем PHP. Актуальная инструкция —
[php/README.md](php/README.md). Ниже сохранена техническая справка Python-варианта;
она не является текущим планом установки и не требует смены тарифа.**

Целевой адрес: **https://analytics.lavka-speciy.com**. Хостинг ADM.TOOLS,
аккаунт `lavkasp`, тариф «Быстрый». Пользователь подтвердил SSH, cron и наличие
`/opt/alt/python312/bin/python3.12`. Системный `python3` версии 3.6.8 не используется.

**Статус:** исходники и установщик готовы для проверки на хостинге. Публичный запуск,
DNS, сертификат, поддержка CGI и подключение к живой БД ещё не подтверждены.
Наличие SSH само по себе не подтверждает CGI. Публикация Codex-среды не разворачивает сайт.

**Ограничение подтверждено скриншотом панели:** в разделе «Настройки веб-приложения»
ADM.TOOLS требует переход на «Бизнес хостинг» для запуска Python-приложения.
Покупка/смена тарифа не выполнялась. Пользователь выбирает штатный запуск Python
на «Бизнесе» либо PHP-адаптацию на «Быстром». Описанный ниже CGI-способ — технический
вариант для провайдера, который явно его поддерживает; он не подтверждён и не должен
использоваться для обхода ограничений тарифа. `wsgi_entry.py` — точка входа для
штатного WSGI runner, если его предоставляет выбранный тариф.

## Размещение

Панель должна назначить поддомену отдельный пустой document root. Не меняйте корень
основного магазина. На тарифе указан один сайт: уточните возможность отдельного
поддомена/хоста в рамках этого сайта, прежде чем менять тариф или покупать услуги.

```text
~/analytics-app/spice-analytics/   Python-код и .venv, вне всех document root
~/analytics-private/              SQLite, пароль и source.json, каталог 700
~/analytics-backups/              закрытые резервные копии
<document root поддомена>/         только analytics.cgi, .htaccess и static/
```

PHP магазина не меняется. Кабинет использует Python CGI: отдельный короткий процесс
на запрос, без Docker, Uvicorn-демона, дополнительных открытых портов и root-доступа.
Этот способ требует ExecCGI/.cgi и mod_rewrite на хостинге. Нельзя заменять его
постоянным фоновым сервером без проверки правил тарифа. Если CGI запрещён, установку
остановить и выбрать поддержанный провайдером способ запуска.

## Установка из Git

Через WebSSH/SFTP разместите содержимое ветки `analytics-demo` репозитория
`andrey-martyn/test1` в `~/analytics-app`. Если HTTPS-clone доступен аккаунту:

```sh
git clone --branch analytics-demo --single-branch https://github.com/andrey-martyn/test1.git "$HOME/analytics-app"
cd "$HOME/analytics-app/spice-analytics"
bash hosting_bootstrap.sh
```

Команда clone не предназначена для уже существующего каталога. Если репозиторий
приватный, загрузите ZIP из авторизованного GitHub через панель/защищённый SFTP
либо настройте отдельный read-only deploy key. Не делайте репозиторий публичным
ради установки, не вставляйте токены в URL и не передавайте их в чат.

Далее задайте **реальный полный путь**, назначенный панелью поддомену:

```sh
.venv/bin/python deploy_hosting.py --webroot '/полный/путь/из/панели' --data "$HOME/analytics-private" --url https://analytics.lavka-speciy.com
export ANALYTICS_DATA_DIR="$HOME/analytics-private"
.venv/bin/python app.py --init-password
.venv/bin/python sync_mysql.py --configure
.venv/bin/python sync_mysql.py
```

Установщик отказывается изменять непустой document root. Ввод паролей скрыт.
`ANALYTICS_DATA_DIR` в созданном CGI-лаунчере уже прописан абсолютным путём; экспорт
нужен CLI-командам в текущем терминале. Настройка реальных подключений на хостинге
не должна заменять песочницу или её пароль. Использовать копию старой выгрузки для
объявления «живого подключения» нельзя.

Если домен отдаёт 500/503 или текст исходника CGI, не переносите базу в публичную
папку. Проверьте поддержку CGI, права запуска, shebang, журнал ошибок и сертификат.
Gateway возвращает общее сообщение без traceback/контактов/паролей. Подробная
проверка зависимостей выполняется через SSH командой из hosting_bootstrap.sh.

## Доступ к MySQL

Отдельному пользователю достаточно **SELECT только на эти таблицы**:

```text
oc_order
oc_order_product
oc_order_option
oc_order_total
oc_order_history
oc_order_status
```

Имена и контакты берутся из сохранённого заказа, отдельный доступ к `oc_customer`
не требуется. Пароли покупателей, администраторы, сессии и настройки магазина
не запрашиваются. Если префикс отличается от `oc_`, укажите его при настройке.
Если панель даёт только права на всю БД, попросите поддержку ограничить SELECT
этими шестью таблицами; права INSERT/UPDATE/DELETE/DDL не требуются.

Локальный Unix-сокет либо loopback/SSH-туннель поддерживаются. Для удалённого
сервера MySQL обязательны TLS, проверка CA и имени хоста; при необходимости нужен
предоставленный хостингом CA-файл. Режима отключения проверки сертификата нет.
Исходный адрес БД из phpMyAdmin не доказывает возможность такого TLS-подключения:
это проверяется отдельно. Не включайте открытый MySQL-доступ «для всего Интернета».

Настройки находятся в `~/analytics-private/source.json` с правами 600. Их создаёт
интерактивная команда `--configure`, а не Git. Значения не отправляются в браузер.

## Расписание

После успешного первого импорта добавьте задачу **каждые пять минут** в раздел cron
ADM.TOOLS. Подставьте абсолютные пути вместо `~`: cron не использует текущее окружение.

```text
*/5 * * * * /ABS/analytics-app/spice-analytics/.venv/bin/python /ABS/analytics-app/spice-analytics/sync_mysql.py --config /ABS/analytics-private/source.json --database /ABS/analytics-private/analytics.sqlite3 >> /ABS/analytics-private/sync.log 2>&1
```

Синхронизация полностью сверяет шесть таблиц. Так обнаруживаются старые изменения,
удаления и правки строк товаров, даже если модуль не меняет `date_modified` заказа.
При текущих ~5 тыс. заказов это практичный начальный режим; фактическую длительность
и нагрузку нужно замерить на хостинге и при необходимости увеличить интервал.
Параллельные задачи исключены файловой блокировкой.

InnoDB читается в read-only consistent snapshot. Для MyISAM выполняются два чтения
с паузой и сравнением всех данных; при расхождении до трёх повторов. Это снижает
риск неполной копии, но **не даёт транзакционной гарантии MyISAM**. Оформление
покупок не блокируется. Неполные/нестабильные данные не заменяют последний снимок.
Строго атомарный источник потребовал бы согласованной резервной копии/реплики либо
изменений на стороне магазина — в текущую установку они не входят.

SQLite заменяется в одной транзакции. CRM, правила, объединения и GA4 сохраняются.
Приложение замечает новую ревизию; открытая вкладка проверяет обновления раз в минуту,
не перерисовывая открытую карточку с редактируемой заметкой. Дата успеха и ошибки
показаны в настройках. Сбой источника оставляет доступной предыдущую копию.

## HTTPS и пароль

Включите сертификат поддомена в панели и редирект HTTP→HTTPS. Приложение проверяет
канонический host, same-origin запросы, ставит Secure/HttpOnly/SameSite=Strict cookie,
no-store и noindex. Пароль — scrypt; сессии и ограничения попыток хранятся в закрытой
SQLite и переживают CGI-процессы. Смена пароля отзывает все сессии, срок сессии 12 часов.
Внутри закрытого кабинета настоящие имена видны сразу; кнопка скрытия остаётся.
Автономное Git-демо остаётся обезличенным. Конфигурация `ANALYTICS_PUBLIC_URL` нужна
также при альтернативном запуске через ASGI/reverse proxy, если он поддержан тарифом.

## Копии и проверка после запуска

```sh
.venv/bin/python backup.py --data "$HOME/analytics-private" --destination "$HOME/analytics-backups"
```

Команда использует SQLite Backup API, проверяет целостность и сохраняет CRM вместе
с закрытыми конфигурационными файлами. Копии не содержат активных сессий. Храните
их вне document root; автоматическое удаление копий не выполняется. Настройте
ежедневный cron и согласованную ротацию после замера размера/свободного места.

На **реальном адресе** после установки проверить:

1. HTTP перенаправляется на HTTPS с действительным сертификатом.
2. Без входа API возвращает 401, страница просит пароль, база/конфиги не выдаются.
3. После входа видны реальные имена, состав и суммы известных заказов.
4. Новый реальный заказ и изменение его статуса появляются после cron.
5. Отметка CRM сохраняется после следующей синхронизации и повторного входа.
6. Отказ доступа к БД показывает ошибку и сохраняет прежние данные; затем доступ восстановить.
7. Запуск не меняет витрину, оформление заказа или данные магазина.

В песочнице проверяются unit/browser/CGI-тесты и отдельный настоящий MySQL 8.4
с синтетическими данными (`tests/mysql_check.py`). Это не заменяет пункты выше
на живом хостинге. До их выполнения нельзя объявлять сайт опубликованным.
